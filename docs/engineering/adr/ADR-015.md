# ADR-015 — Deploy automático do backend no servidor próprio com GHCR + Watchtower

**Data:** 2026-11-10
**Status:** Aceita — aprovada pelo CTO em 2026-11-10.
**Autores:** Isaque Souza (CTO), Claude Code

---

## Contexto

O backend saiu do Render (2026-11) e roda num servidor Linux próprio do CTO com Docker Compose e
Tailscale Funnel. No Render o push na `main` gerava o deploy; no servidor próprio, nada no repositório
atualiza o backend — o CI (`.github/workflows/ci.yml`) só valida. Cada merge exigia entrar no servidor,
`git pull` e rebuild à mão, e o frontend (Vercel, automático) podia ficar à frente do backend.

O deploy do PR #79 (2026-11-09) também mostrou que migrations entram no boot sem ninguém olhando
(KI-058): qualquer automação precisa garantir um ponto de volta para o banco.

---

## Alternativas Avaliadas

### Opção A — Continuar manual

**Prós:** nenhuma peça nova; o CTO escolhe a hora de cada deploy.
**Contras:** esquecível; frontend e backend ficam fora de sincronia; build no próprio servidor.

### Opção B — GitHub Actions entra no servidor por SSH

**Prós:** deploy imediato após o CI.
**Contras:** exige expor SSH ao runner (chave privada no GitHub, acesso pela tailnet ou porta aberta) —
amplia a superfície de ataque do servidor de produção.

### Opção C — CI publica imagem no GHCR, Watchtower no servidor puxa (escolhida)

**Prós:** o servidor só faz saída (pull), sem credencial de produção no GitHub; só imagem que passou em
todos os gates bloqueantes é publicada; tag `:<sha>` permite fixar versão para rollback; o hook
`pre-update` do Watchtower permite backup antes de cada troca.
**Contras:** atraso de até 5 min (polling); depende de um projeto de terceiros (o Watchtower original foi
arquivado em 2025-12 e quebra no Docker 29+ — usamos o fork mantido `nickfedor/watchtower`, versão fixa).

---

## Decisão

**Escolhemos: Opção C.**

- Job `publish_image` no `ci.yml`: só em push na `main`, depois de `backend`, `coverage`, `build` e
  `docker`; publica `ghcr.io/isaque-souza/fluxoly:latest` e `:<sha>` com o `GITHUB_TOKEN`.
- `deploy/docker-compose.yml`: serviço `fluxoly` (imagem do GHCR, volume `/data`, `.env`, healthcheck em
  `/health`, porta só em `127.0.0.1`) e serviço `watchtower` (`WATCHTOWER_LABEL_ENABLE` — só mexe em
  container com a label —, intervalo de 300 s, limpeza de imagens antigas, hooks ligados).
- Hook `pre-update` roda `scripts/backup_pre_update.py` no container antigo: copia o banco para
  `/data/backups/backup-pre-update-*.db` (reusa `criar_backup`, retém os últimos 20). Se a cópia falhar,
  sai com 75 e o Watchtower não atualiza nessa rodada — nenhuma migration entra sem backup.

O fator decisivo foi não colocar credencial de acesso ao servidor de produção no GitHub.

---

## Consequências

### Positivas

- Merge na `main` chega ao backend sem passo manual, só com CI verde.
- Backup automático antes de cada atualização.
- Rollback rápido fixando `:<sha>` no compose.

### Negativas / Trade-offs aceitos

- Migrations aplicadas sem acompanhamento — o runner continua sem trava entre workers (melhoria apontada no
  KI-058). Registrado no KI-060.
- Alguns segundos fora do ar a cada atualização (1 instância, SQLite).
- Imagem pública no GHCR (o código já é público; segredos e banco ficam no `.env` e no volume).
- `docker.sock` montado no Watchtower dá a ele controle do Docker do host — aceito por ser imagem fixa de
  projeto conhecido.

### Condições de revisão

- Se houver mais de um servidor/cliente em produção, ou se uma migration precisar de janela de manutenção.
- Se o fork do Watchtower deixar de ser mantido.
